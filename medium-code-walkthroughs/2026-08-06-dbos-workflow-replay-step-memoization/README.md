# DBOS workflow replay vs. step memoization — code walkthrough

Companion code for the 2026-08-06 Medium article **"I Crashed My AI Agent Between Two Steps. DBOS Reran the Workflow From the Top — but Not the Steps It Had Already Finished."**

It demonstrates DBOS Transact's durable-execution recovery semantics on a local, zero-config SQLite database: on crash-and-restart the `@DBOS.workflow` **body re-executes from the top**, while already-completed `@DBOS.step` calls are **memoized (never re-run)**.

## Files

- `agent.py` — a three-step "research agent" workflow that hard-crashes (`os._exit(1)`) between step 2 and step 3 on the first pass.
- `run.py` — starts the workflow (pass `start`) or reattaches to the recovered one (pass `resume`).
- `inspect_db.py` — reads the DBOS checkpoint tables (`workflow_status`, `operation_outputs`) straight out of the SQLite file.
- `diagram1-crash-recovery.svg`, `diagram2-where-durability-lives.svg` — the article figures.
- `article.md` — the full article.

## Setup

```bash
python3 -m venv venv          # Python 3.11 used here
. venv/bin/activate
pip install "dbos==2.29.0"
```

No database server, no Docker, no API keys. With no `database_url` in the config, DBOS creates and migrates a local `research_agent.sqlite` file on first launch.

## Run it

```bash
rm -f effects.log allow_finish.flag research_agent.sqlite*
python run.py start          # runs steps 1-2, then hard-crashes before step 3
touch allow_finish.flag      # lets the recovered run get past the crash guard
python run.py resume         # DBOS.launch() recovers the pending workflow
cat effects.log
python inspect_db.py
```

Step 2's memoized blob decodes to the integer it returned before the crash:

```bash
python3 -c "import base64,pickle; print(pickle.loads(base64.b64decode('gARLHC4=')))"
# 28
```

The recovered run reused that `28` without ever re-running `gather`. In `effects.log`, `STEP plan` and `STEP gather` appear only once (run 1), while `BODY start` and `BODY after gather` appear twice — proof that the body is replayed but completed steps are not.

## Takeaway

The workflow body is the unit of deterministic replay; the step is the unit of exactly-once execution. Put every side effect (API calls, writes, messages) **inside a step**, or it will fire again after a crash-and-resume.
